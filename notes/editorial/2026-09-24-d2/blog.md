你可能已经让 agent 帮忙整理过资料：读几份公开文档，列成一张表。结果不错，于是很自然地想往前推一步——既然整理得好，能不能顺手把结论发给同事、把文件改掉、把工单建好？

这一步的差别很大。**决定能不能交给 agent 的，不是它有多聪明，而是这一步出错之后能不能撤回。** 按这个标准，手上的任务大致能分成三类。

## 1. 可撤回的信息整理：读、找、摘

这一类只读取和重组已有信息，不改变任何外部状态：读文件、检索、做摘要、列提纲、写一份草稿。做错了，丢掉重来即可。

Claude Code 的权限文档把这类操作单独对待：在工作目录及附加目录内，只读的文件读取和 Grep 不需要批准；shell 命令则通常需要批准，官方只对一组只读命令免去批准。也就是说，官方默认就把「只看」和「动手」分开了。

例子：把十几份公开公告整理成一张发布时间表。这件事适合交给 agent，因为最坏的结果是一张需要重做的表。

但有一点要注意：**可撤回不等于可信**。摘要里完全可能混错日期、漏掉条件。这一类可以放手让 agent 跑，结论仍要抽样核对，不能直接拿去支撑一个决定。

## 2. 需复核的业务建议：判断、排序、方案

这一类不改变外部状态，但会影响你的决定：先处理哪个客户、先改哪个模块、这套方案值不值得做。agent 可以提出建议，但建议不应该自动变成动作。

两个公开工具的做法值得参考。Claude Code 提供 plan 模式，先给出计划、由你确认再执行；GitHub Copilot 的 cloud agent 会先在一个分支上研究仓库、制定实现计划并修改代码，你可以查看 diff、反复迭代，觉得可以了再创建 pull request。共同点是把决定权留在一个明确的位置。

例子：agent 根据公开数据建议「这三类工单应该优先处理」。这是排序建议，可以进你的待办，但不应该自己变成「已通知相关同事」。

边界：这一类需要一个明确的签字点。没有写清楚的验收标准，就不要让它进入下一环。

## 3. 影响外部状态的动作：发出、改动、提交

这一类一旦执行，就留下外部痕迹：发邮件、改数据库、提交工单、付款、发布内容、通知客户。做错了，成本不再是一张表。

对应的控制手段也更重。Claude Code 的 Bash 沙箱用文件系统隔离和网络隔离来限定 agent 能碰什么：你可以规定哪些目录、哪些域名可访问，也可以让沙箱内的命令自动放行。文档同时给出了「逃逸」设置和一份安全限制说明，提醒沙箱并不是绝对保障。GitHub Copilot 的 cloud agent 则需要单独配置网络访问、防火墙与 secrets。

例子：把整理好的名单导入系统并批量发信。即使 agent 能做完，也建议由人逐项确认目标范围和发送内容。

边界：这一类默认不放，或者只在限定范围内放行，并保留一条回退路径。

## 一张任务分级与人工介入表

| 任务类型 | 典型例子 | 谁先动手 | 人工介入点 | 可以放手的条件 |
| --- | --- | --- | --- | --- |
| 可撤回的信息整理 | 读文件、检索、做摘要、写草稿 | agent | 抽样核对结论 | 输入不敏感，输出可丢弃 |
| 需复核的业务建议 | 排序、推荐、判断、方案 | agent 先提议 | 人确认后才进入下一步 | 有写清楚的验收标准 |
| 影响外部状态的动作 | 发邮件、改数据、建工单、付款、发布 | 人 | 执行前逐项确认 | 有回滚路径且范围受限 |

这张表不是一次填完就长期有效的授权书。三类之间会滑动：同一条链路上，从整理到建议再到动作，权限要在每一环重新判断，不能拿第一次的「可以」贯穿到底。

## 适用边界

沙箱、权限规则和审批点降低的是风险，不是把风险清零。上面引用的两份官方文档都单列了限制与注意事项，配置了隔离也不等于不会出错。

本文的例子是说明划分方法的假设场景。我没有对这些产品做安全测试，也不宣称任何产品提供某种保障。规则名称、权限模式和默认行为都可能随版本变化，用之前请回到官方文档核对当前说明。

今天可以只做一件事：找出你最近一次交给 agent 的任务，写下它属于哪一类。如果它其实落在第三类，先把它退回到第一类——让 agent 只做整理，把动作留给你自己。
