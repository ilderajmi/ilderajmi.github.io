JARED · 工作方法

把工作交给 agent 之前，先分清这三类任务

你可能已经让 agent 帮忙整理过资料：读几份公开文档，列成一张表。结果不错，于是很自然地想往前推一步——既然整理得好，能不能顺手把结论发给同事、把文件改掉、把工单建好？

决定能不能交给 agent 的，不是它有多聪明，而是这一步出错之后能不能撤回。

01 · 可撤回的信息整理

读文件、检索、做摘要、列提纲、写草稿，这类操作只读取和重组已有信息，不改变任何外部状态。做错了丢掉重来即可，最坏结果是一张需要重做的表。

Claude Code 的权限文档就把这类操作单独对待：工作目录内只读的文件读取和 Grep 不需要批准；shell 命令则通常需要批准，官方只对一组只读命令免批准。官方默认也把「只看」和「动手」分开了。

但要记住：可撤回不等于可信。摘要完全可能混错日期、漏掉条件，结论仍要抽样核对。

02 · 需复核的业务建议

判断、排序、推荐、方案，这类输出不改变外部状态，却会影响你的决定：先处理哪个客户、先改哪个模块、这套方案值不值得做。

Claude Code 提供 plan 模式，先给计划、你确认再执行；GitHub Copilot 的 cloud agent 会先在分支上研究仓库、制定计划并改代码，你可以看 diff、反复迭代，再决定要不要创建 pull request。共同点是把决定权留在一个明确的位置。

边界：这一类需要一个签字点。没有写清楚的验收标准，就不要让它进入下一环。

03 · 影响外部状态的动作

发邮件、改数据库、提交工单、付款、发布内容、通知客户，一旦执行就留下外部痕迹，做错了成本不再是一张表。

控制手段也更重：Claude Code 的 Bash 沙箱用文件系统隔离和网络隔离限定 agent 能碰什么，并单独给出安全限制说明；GitHub Copilot 的 cloud agent 需要单独配置网络访问、防火墙与 secrets。

边界：这一类默认不放，或者只在限定范围内放行，并保留一条回退路径。

一张分级表

信息整理 → agent 先动手，人抽样核对结论。

业务建议 → agent 先提议，人确认后才进入下一步。

外部动作 → 人先动手，执行前逐项确认。

三类之间会滑动。同一条链路上，权限要在每一环重新判断，不能拿第一次的「可以」贯穿到底。

沙箱和审批点降低的是风险，不是把风险清零。本文例子是说明方法的假设场景，我没有对这些产品做安全测试，也不宣称任何产品提供某种保障；规则与默认行为请以官方文档当前说明为准。

今天只做一件事：找出你最近一次交给 agent 的任务，写下它属于哪一类。如果它其实落在第三类，先退回第一类——让 agent 只做整理，把动作留给你自己。
